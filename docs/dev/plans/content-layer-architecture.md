# Content layer architecture

## Goal

One Reikai-owned content layer, shared behavior and shared UI over a neutral `Entry` vocabulary, that serves manga and light novels so a feature is written once and reaches both. It extends the shipped Entry* UI-leaf seam ([unified-content-ui.md](unified-content-ui.md)) down into the ScreenModel behavior, replaces the current dead-Mihon-file policy with one a solo+AI workflow can trust, and folds the reader unification in as its final phase. The end state: novels stop being a re-typed copy of the manga stack, and there are no dead files an edit can silently land in.

## Why

Two problems with one root cause: the shared seam is drawn too high (UI only) and too informally (ad-hoc reroutes, no enforcement).

- **Duplication is the daily cost.** The light-novel port copy-adapted the manga stack, so `NovelDetailsViewModel` (1421 lines today) is largely `MangaViewModel` re-typed onto `Novel`. The two details ScreenModels are roughly 70-75% congruent, and the multi-source merge methods (`selectSource`, `splitSources`, `reorderSources`, `removeSourcesFromLibrary`, and the rest) are line-for-line twins. The shipped Entry* work shared the UI leaves but left this behavior forked, so every manga/novel change is two edits, and the two sides drift.
- **The sync/bury hazard** (the state that motivated this program; the inert-tombstone pattern below has since been retired in favour of delete-and-manifest). There were four distinct integration patterns against Mihon: in-place delegation (the details screen, `// RK` islands calling Entry* components), inert-leaf tombstones (`MangaCoverDialog`, `TrackInfoDialog`, `GlobalSearchCardRow`, `DownloadQueueViewModel`, marked `// RK: inert`), whole-screen reroutes that left Mihon composables dead **and unmarked** (`HistoryScreen`, `UpdatesScreen`, `SourcesTab`, `MigrateSourceTab`, bypassed by `ReikaiHistoryScreen`/`ReikaiUpdatesScreen`/`reikaiSourcesTab`/`reikaiMigrateSourceTab`), and pure novel twins with no Mihon equivalent. Nothing flags an off-render-path Mihon file that changed upstream, so a synced fix can land on a dead file and do nothing, and an edit can be made against a file that is never rendered.
- **Solo+AI needs a different shape.** One obvious place to write shared behavior, no dead-file traps, and a seam that fails loudly at compile time when upstream drifts.

## Approach

Three layers, one hard ownership rule.

- **Engines stay split and unequal.** Mihon's manga engine (`Manga` model, its repositories and source/library/download machinery) stays upstream-tracked and minimally patched. Reikai's novel engine (`Novel` model, plugin host, novel repositories) stays fully Reikai-owned. They are never merged; merging them would re-type Mihon's whole stack and sever upstream flow.
- **Adapters are the only seam.** A `MangaEntryAdapter` reads Mihon's `MangaViewModel`, which stays **live** and on the render path, so the manga engine keeps syncing and is never bypassed. A `NovelEntryAdapter` reads the novel engine, and `NovelDetailsViewModel` dissolves into that adapter plus the shared behavior. The adapter is the single point of Mihon coupling; a renamed upstream field breaks it at compile time, not in a pixel hunt.
- **The content layer is Reikai-owned and holds the shared behavior plus the Entry* UI**, written once and driving both content types over the `Entry` interface and a set of typed capability slots.

**The shared behavior spine** (both types): chapters list, selection (toggle / all / invert / range), filter / sort / display, download actions, mark read / previous / bookmark / delete, tracking with tracker autofill, categories, cover dialog, custom-info edit (already routed through the neutral `EntryEditInfoUi`), hide / unhide chapters, the whole merge / multi-source subsystem (already sharing `MergeGroupRepository` at the domain layer), favorite / duplicate, and refresh.

**Capability slots** are typed, not nullable fields, so the shared model never rots into nullable soup. Each mapper fills only what applies.

- Manga: page previews, related-manga carousel, gallery / adult metadata, E-Hentai account, and scanlator filtering. Scanlator filtering is modeled as a **content-type-gated** capability rather than a manga-forever one: novels can light it up later (translator groups) once the novel schema carries a group column. It is not a free port from tsundoku, whose novels inherit the manga `scanlator` field only because tsundoku makes novels be manga rows, a design Reikai rejects.
- Novel: paged-source page selector and the plugin-installer lifecycle.

**Reconciliations the interface must handle**, surfaced by comparing the two ScreenModels: the source id is `String` for novels and `Long` for manga, and the two entry id spaces are disjoint (manga positive `Long`s, novels currently disguised as negative `Long`s in shared code), so the shared layer resolves both to a neutral sealed `EntryId` and retires the disguise (see the novel-data-model decision below); the per-chapter download state differs (novels derive a downloaded-id set from the disk cache, manga carry per-chapter `DownloadManager` status), which is resolved together with the download-subsystem unification (Road B), though the library-level count is already symmetric on both sides (`DownloadManager.getDownloadCount` is a one-line delegate to the same disk-backed cache the novel side reads directly, so the library surface has no reconciliation to make here); the merged-display field is named differently per side; the filters are per-axis TriState prefs on both sides, overlapping 1:1 bar manga's `intervalCustom` and novel's `lewd` (an earlier "one `Long` flag versus three TriState calls" premise was disproved by the library pipeline comparison); and the cross-source "same chapter" predicate differs (novel `>= 0.0` vs manga `isRecognizedNumber`).

**Dead-file policy** (the change to the sync workflow):

- A pure-UI Mihon file that is fully replaced by a shared component is **deleted**, not kept inert. The three-way diff base still lives in the `refs/mihon` clone, so a retained dead copy buys nothing but a misedit target. This supersedes the "copy, never move, mark `// RK: inert`" rule for pure-UI files.
- An engine file (a ScreenModel, repository, or the source manager) stays **live** and minimally patched, adapted at the seam. These are the real sync surface and are never taken off the render path.
- One tracked **off-path manifest** lists every Mihon path deleted or rerouted plus its replacement, and a sync-time script diffs those paths across each upstream's sync range and fails loudly if one changed. This is the enforcement the current process lacks, and it generalizes to two upstreams (Mihon plus tsundoku, once the reader migrates).

**Sequencing** is one surface at a time, fully cut over and verified on-device (debug and minified) before the next: details first (the keystone adapter, and the cleanest), then library, then browse, then migrate and global search. Each surface extracts the shared behavior first, then folds the novel ScreenModel onto it, then deletes the replaced pure-UI Mihon files and updates the manifest. Extracting the shared behavior before dissolving the novel model is what keeps each surface incremental and never gambles the whole surface on one big adapter.

**The remaining sequence, after the 2026-08-06 ruling** (see Status for what forced it): close out the migrate surface, run the takeover behaviour inventory on the three taken-over surfaces (migrate, then details and library), redo the surfaces below the behavior seam, then the reader phase. Browse took a verb collapse first and was scouted out of the redo on a pager premise that has since expired, so it is back in it under the fifth amendment below; the history-and-updates takeover ([recents](content-layer-recents-surface.md), which carries the combined Recents feed) has since shipped with its closing inventory run. The browse takeover has shipped too, closing inventory included. What remains is the reader phase, now itself a takeover under the sixth amendment below, and then Road B as the
Downloads slice, which closes the program (owner, 2026-09-03: downloads goes last, since it is the heaviest upstream churn of the two and nothing else waits on it). A cut-over surface is not finished until its inventory is recorded, which is the completion bar added to Decisions below.

**The reader is folded into this program** rather than a separate branch, and after its 2026-09-03 scout it is an orchestration takeover rather than a fold-in. One host Activity keeps the window responsibilities, a Reikai-owned engine owns navigation, position, chrome and the action verbs, and two providers sit under it: `ReaderViewModel` live as the manga provider, and a net-new novel provider whose viewer is tsundoku's native text renderer lifted onto Reikai's novel domain. It is the largest and riskiest piece, and it runs next, with Road B closing the program behind it. The shared reader chrome ([unified-reader.md](unified-reader.md)) is superseded by it. The manga image viewers still stay Mihon and are not decoupled, which here is a hard line rather than a preference: decoupling them is the reverted Option A. Scope, rulings and sequencing live in [content-layer-reader-surface.md](content-layer-reader-surface.md).

## Decisions & tradeoffs

- **Push the seam to behavior, not just UI.** The shipped Entry* work shared the UI leaves but left the ScreenModels forked, which is the bulk of the duplication. The content layer owns the behavior too.
- **"Dissolves" means reshaped behind an adapter, not deleted.** Recorded after the fact, because the details surface promised its novel model would be "gone" and it is still 1421 lines, live behind `NovelEntryAdapter`. What actually collapses is the UI body and the behavior contract; both per-type models stay live, one because it is Mihon-synced and the other because its engine work has nowhere else to go. Plan later surfaces on that expectation, and read every "dissolves" below in that sense.
- **Adapter over the live `MangaViewModel`; the novel ScreenModel dissolves.** The hard rule is to never reimplement Mihon's core spine (read / download / filter / sort / selection) in the shared layer. Doing so is the maximal-dedup option but it forks Mihon's manga behavior and turns every upstream change into a hand-port forever, a permanent sync tax a solo developer cannot carry. So the manga model stays live and syncing, and only the seam adapter is Reikai code, compile-caught on drift.
- **Amendment, library surface only (2026-07-22): the shared layer owns selection and pipeline orchestration.** The spine rule above still holds for read, download and the action verbs, which stay in the live per-type models. It is narrowed for the library, because the "All" chip on the roadmap (one interleaved manga plus novel list, which that roadmap line says this phase delivers) makes a mixed selection unavoidable: a range-select spans rows of both content types, so neither ScreenModel can compute it alone, and a `Set<Long>` cannot even name a mixed selection unambiguously. So the library's shared engine owns list assembly, the pipeline call order, category bucketing, selection as `Set<EntryId>`, and dispatch by content type; each content type keeps a provider owning its favourites flow and its action verbs, and for manga that provider **is** the live `LibraryViewModel`, still on the render path, still calling Mihon's interactors, still synced. What narrows the rule here rather than everywhere: `LibraryViewModel` already stands at 1334 lines against upstream's 825, with 78 `// RK` islands and 927 diff lines, so the sync tax the rule protects is largely already paid on this one file, and the shared-pipeline steps already moved filter, sort, search and grouping into shared kernels it calls. **This is an exception scoped to the library, not a general licence**; the rule stands unamended for details, browse and migrate. The fuller version (the shared layer owning the action verbs too) was parked here and has since been adopted, see the amendment below.
- **Second amendment, library surface only (2026-07-27): the full takeover, and the library is built All-first.** The parked fuller version above is adopted. The shared layer owns the action verbs as well as assembly, dispatching to per-type interactors at the bottom, and `LibraryViewModel` is deleted and manifested at the end. **(Settled 2026-08-22, against that last clause: the file stays live.** The owner ruled that delete-and-manifest applies only when a whole file is dead with no callers; otherwise the dead code is deleted and the live remainder stays put, moves to a Reikai-owned file, or is renamed and manifested. `LibraryViewModel` has real callers through `MangaLibraryAdapter`, so it is an engine file, stays synced, and is not manifested. [content-layer-library-surface.md](content-layer-library-surface.md) was right; this clause was not. The library surface is finished on that count.) The library screen is built for the mixed case first, so the Manga and Novel chips become filter predicates over one assembled list and All is the absence of a filter, rather than a composite stitched over two states. What changed the decision is measurement rather than appetite: upstream touched `LibraryViewModel` 12 times in 12 months (370 added, 313 deleted), but the verbs specifically only twice, with `markReadSelection`, `setMangaCategories` and `openChangeCategoryDialog` untouched for a year. The churn lands on list assembly, which an All-first rebuild takes over regardless, so the verbs are the cheap part rather than the expensive one. Reikai's copy was already 1076 lines against upstream's 837 with 76 `// RK` markers and 851 diverging lines, so every library sync was already a hand-merge, not a copy. **Two hard lines hold.** Interactors and repositories stay Mihon's and stay synced; the takeover stops at orchestration, and any step that starts reimplementing what `setReadStatus` or `DownloadManager` does has gone too far. And this widens the never-manifest-an-engine-file rule for one file, deliberately, which is why the manifest's enforcement was made a hard stop first (see [off-path-manifest.md](../off-path-manifest.md) "What enforces this"). **Still scoped to the library**; details, browse and migrate keep the original rule.
- **Third amendment, migrate surface only (2026-08-02): the flow takeover.** The migration flow (screens, step sequence, orchestration) becomes Reikai-owned and serves both content types, superseding the migrate part of the "details, browse and migrate keep the original rule" sentences in the two library amendments above. What forced it: the manga and novel flows diverged structurally (the single-entry fork, the flag moment, the override protocol, the safety chrome), upstream migration fixes reach manga only, and no smaller option removes the step fork, because the fork lives in orchestration. The price was measured before the ruling: `mihon/feature/migration` took ~18 upstream commits in 12 months, ~13 of them behavior fixes, the highest churn of any taken-over surface; each future fix on a taken-over file becomes a manifest-guarded triage instead of a mechanical merge. Hard lines, same shape as the library's: `MigrateMangaUseCase`, `MigrationFlag`, the smart-search engines, and every interactor below them stay Mihon's and synced; `MigrateNovelUseCase` stays the novel sink; global search (`SearchViewModel`, `GlobalSearchViewModel`) is excluded entirely. The widening of the never-manifest-an-engine-file rule extends to the flow's ScreenModels, deliberately, as the library takeover established. Scope detail, the ruled design picks, and the cutover sequencing live in [content-layer-migrate-surface.md](content-layer-migrate-surface.md).
- **Fourth amendment, history and updates only (2026-08-08): the recents takeover, built All-first.** The two feed surfaces become one Reikai-owned engine that also serves the combined Recents feed requested in `unseensnick/Reikai#57`, superseding the history-and-updates part of the 2026-08-06 redo ruling by naming what the redo is. What forced it is the duplicate-implementation class the redo ruling was written against, measured on these two screens: the novel feed filters nothing in SQL where the manga feed filters four axes, both feeds resolve category membership per row in Kotlin behind a screen-lifetime cache, and list-level state (search, loading, dialogs, selection, clear-all) is stored once per content type on a single screen, which is why clear-all prompts twice and the novel feed gates the manga chip's spinner. The price is the lowest of any takeover so far: twelve months of upstream churn is five commits on history, all cross-cutting mechanical, and thirteen on updates of which three are behaviour. Hard lines, same shape as the library's and the migrate flow's: the interactors and repositories stay Mihon's and synced, and `UpdatesViewModel` and `HistoryViewModel` stay live as the manga providers rather than being manifested, since the churn gives no case for absorbing them. Two rules bind here beyond the program's: the library's **All-first** ruling is adopted whole (All is the real feed, the chips are predicates over it, anything describing the list is one value), and every keyed structure keys on `EntryId` rather than a raw `Long`, because the id spaces overlap and a `Long`-keyed map over a mixed feed cross-wires silently. Scope, the ruled design picks and the sequencing live in [content-layer-recents-surface.md](content-layer-recents-surface.md).
- **Fifth amendment, browse only (2026-08-27): the takeover, built All-first.** The 2026-08-09 decline is overruled and browse rejoins the redo. It rested on a mechanism premise, that a takeover would have to reimplement one of the two pagers, and that premise was wrong on re-reading: Paging 3 is upstream's own mechanism (`BrowseSourceViewModel` in `refs/mihon` builds its own `Pager`, `SourcePagingSource` is a bare typealias over androidx `PagingSource`, the artifacts are in Mihon's version catalog), so moving novels onto it adopts the base rather than reimplementing it, and the spine rule never reached pagination. The filter dispatch stays split on mechanism and becomes a typed capability rather than a decline. What forced the ruling is the cost of the behaviour-partial shape, measured on the default chip: `ContentType.ALL` is the default, and under it the hand-wired combined lists drop five upstream extension behaviours (section headers and with them Update all, pull-to-refresh, the install-permission banner, the loading and empty states, and the back-clears-search handler from mihonapp/mihon#2906) and render Last used and Pinned twice on the sources list. The trust bug fixed in `c5c5bc0ea` was the sixth of the same class and was found by accident. Churn was re-measured rather than quoted: 12 commits in twelve months on the source-browse paths and 16 on extensions, no single file above 5, all at or below the synced base. **Browse is two surfaces under this amendment**, which is the part that is easy to mis-plan: the four multi-source lists (sources, extensions, migrate-sources, global search) are All-first in the library's and recents' sense, and the per-source grid is not one of them at all, since a source fixes the content type before the screen opens, so it takes the details surface's shape. Global search comes back into scope as a provider; migration's use of the smart-search engines stays out. Hard lines are unchanged: interactors and repositories stay Mihon's and synced, every per-type model stays live as a provider, and the takeover stops at orchestration. Scope, the ruled design picks and the sequencing live in [content-layer-browse-surface.md](content-layer-browse-surface.md).
- **Sixth amendment, reader only (2026-09-03): the takeover, over one host Activity.** The seam-depth table's "chrome only, the two engines are separate by design" ruling is superseded; it predates the program's settlement, when chrome sharing was the whole ambition. **What makes this surface different from the five before it: the host owns a window, so it cannot exist twice.** Every previous takeover put a shared engine above two live per-type models; here `ReaderActivity` stays the single host for both content types, keeping only what an Activity can own (system bars and insets, cutout padding, orientation, keep-screen-on, brightness, the secure flag, menu visibility, key dispatch), all of which is already content-neutral, and the Reikai-owned engine above it takes navigation, position, chrome state and the action verbs over two providers. `ReaderViewModel` stays live as the manga provider and is not manifested; the novel reader dissolves outright rather than becoming a provider, because its engine is a WebView plus a vendored `core.js` that is being replaced. Three hard lines are specific to this surface, all re-grounded on 2026-09-03 after a scout of tsundoku's settings surface. **The image viewers are never diverged past their five existing `// RK` markers**, because Option A (a single Compose shell with the viewers decoupled behind `ViewerHost` and embedded via `AndroidView`) was built here and reverted on exactly that cost, and the decline is routed around rather than expired; the earlier "byte-identical" wording was already false for two of the three files. **Position is a typed capability, never an `Int`**, with `ReaderChapter.requestedPage` as the one named exception: five places in the current host assume a page index, so sharing an integer page count between a paged medium and a continuous one would be derive-or-do-not-own in its most tempting form, but that one field is read directly by all three image viewers and honouring the rule there would mean editing them. And **the engine owns the viewer contract**, with Mihon's `Viewer` as one adapter under it rather than the interface novels implement, because `ViewerChapters` is three `ReaderChapter`s wrapping manga `Chapter`s and `ReaderPage` has no text field, so a novel viewer cannot implement it without the `Page.text` novels-as-manga mechanism the program rejected at the data layer. **The takeover also owns the settings whose implementation is inside the code being deleted:** the novel reader's seven typographic settings exist only as CSS variables written by the vendored JS and surfaced only in the sheet being removed, so a takeover that ignored them would have shipped a reader with no font choice and no themes. Novels move onto two tsundoku-ported rendering modes, native text and a first-party WebView, and the vendored JS goes in both. **The price is stated rather than borrowed:** this is the highest-churn surface the program has taken over (twelve months at the synced base: 20 commits on `ReaderActivity.kt`, 15 on `ReaderViewModel.kt`, 42 across `ui/reader/`) and simultaneously the least diverged (16 and 46 `// RK` markers, against the library's 76), so the library's "the sync tax is already sunk" argument does not apply and the case rests on the duplicate-implementation cost of two reader hosts plus the fact that the novel half is being rebuilt regardless. Scope, the ruled design picks and the sequencing live in [content-layer-reader-surface.md](content-layer-reader-surface.md).
- **Divergent bits are typed capability slots**, never nullable fields or per-type forks.
- **A shared component either derives a piece of state or it does not own it.** Handing both content types one mutable cell and trusting each to read it correctly is the same "two answers to one question" defect in a new costume: the sharing is real, the behaviour is still forked, and nobody rules on the fork because it looks like shared code. The case that produced the rule: `EntryMergeGroupHost` derived its group ids and its source chips but left the selected chip a free cell beside them, so migrating a selected source out of the group crashed the manga chapter pipeline on an unguarded lookup and silently rendered the migrated-away source on novels. Two flows were not enough to fix it either, since a consumer combining them sees the pair disagree for one emission; the group and its selection became one cell. When a shared component exposes state that only some consumers must interpret, either derive it there or leave it with the consumer that owns it.
- **A rule that must hold for both types is pinned once (2026-08-09, superseding the twin-test rule).** The twin rule asked for a second hand-maintained test beside the first, and hand-maintained twins drift: the 2026-08-05 re-audit found 8 tests on `MigrateMangaUseCase` against 24 on `MigrateNovelUseCase`, with the manga copy-into-group branch untested while the novel side treated it as contract. That measurement is the case for pinning once rather than twice. The ladder, in order of preference, is a shared kernel both sides call, then a typed capability the compiler forces both types to answer, then one conformance test parameterized over both adapters; a hand-written pair is the last resort. This binds new work; the historical gap is closed opportunistically, not as a backfill sprint.
- **The never-merged rule covers the implementation, never the rule, and only reaches Mihon twins (owner, 2026-08-10).** The Ownership clause was being read as a blanket exemption, so a twin pair could sit unpinned and nobody ruled on it, which is precisely the drift write-once exists to stop. The count that forced the ruling: 84 files carry a `twin of` marker against two conformance suites in the whole tree, and 67 of those files are Reikai-owned. Since the exemption exists because re-typing Mihon's models breaks hand-porting, it reaches exactly as far as that reason: a Reikai file twinning a Reikai file was never covered and is ordinary duplication. An engine twin that genuinely is covered still owes the pin-once ladder, and a `twin of` marker now names which rung pins it, paid the next time either half is touched rather than as a sweep. **Merging the engines outright was considered and declined the same day**, on two measurements: `source-api` is the contract installed extensions compile against, so a manga-shaped source boundary survives any merge and the seam would move rather than disappear; and 166 of the app module's 1099 files reference `Manga`, all of which become permanently hand-merged, ending the verbatim-copy path that keeps the synced base at upstream head. The cheaper form of the same goal is to push the neutral layer down into the Reikai-owned domain twins, which is where the measured drift actually is.
- **Novel data model: separate tables, a neutral `EntryId`, not novels-as-manga.** Novels keep their own `novel*` tables (String sources, plugin-specific fields, and `mangas` left byte-Mihon for clean sync), and the shared layer identifies every entry by a sealed `EntryId` (`EntryId.Manga(Long)` | `EntryId.Novel(Long)`, exposing a `rawId` and a `contentType`), which replaces the negative-synthetic-`Long` disguise that currently leaks into the color cache and shared UI. The sealed form is chosen over a `(ContentType, Long)` pair on purpose: it makes a mismatched (type, id) impossible to construct and gives an exhaustive `when`, which is the same compile-caught safety the whole adapter seam is built on; a `contentType` accessor keeps it interoperable with the existing `ContentType` enum used for filtering and grouping. Tsundoku's novels-as-manga (hash the `String` plugin id to a `Long` source, store novels as `manga` rows) was considered and rejected: it dedups at the data layer but forks `mangas.source` semantics, sprays `isNovelSource()` branches through Mihon's synced engine, risks source-id hash collisions, and couples novel storage to Mihon's manga schema, the opposite of a downstream fork's clean-sync goal. The reader still gains tsundoku's engine, with no data merge, but not through the `source -> page.text` loader bridge this sentence used to name: that bridge only exists because tsundoku added a `text` property to Mihon's `Page` and put `fetchPageText` on `Source` itself, both of which follow from novels being manga rows. Reikai's `Page` has no such field and `ReaderChapter` wraps the manga `Chapter`, so the novel viewer is fed by its own provider instead ([content-layer-reader-surface.md](content-layer-reader-surface.md)).
- **The identity change is code-only; backups are unchanged.** The negative-id disguise is a runtime trick, never persisted: novel rows carry real positive ids, and the merge tables and backups already key on those. So introducing `EntryId` needs no schema migration and no backup-format change, and old backups restore identically. Because the whole program keeps the separate engines and tables, no phase requires a data migration (the reader phase reads the same `novel*` tables through the loader bridge; Road B is a code merge). The one path that would force a painful, backup-breaking data migration, moving every novel row into `mangas`, remapping ids, rewriting foreign keys, and converting every old backup, is novels-as-manga, a further reason against it. Implementation caveat: any rebuildable runtime cache or saved UI state keyed by the old disguised id (the cover color cache, saved scroll or selection state) gets a one-time reset, which is never a backup concern.
- **Replaced pure-UI Mihon files are deleted, not kept inert.** A solo+AI workflow cannot afford dead-file misedit traps; the `refs/mihon` clone holds the diff base, and the off-path manifest plus sync script make a buried upstream change impossible. Engine files stay live. This supersedes the keep-inert rule for pure-UI files.
- **The reader unifies via tsundoku, folded into this program and running ahead of Road B**, with tsundoku accepted as a second upstream for the novel viewer only and a View-based novel reader accepted in exchange for native rendering. The 2026-09-03 scout narrowed what is taken: tsundoku's `NovelViewer` calls twenty-one distinct members of their own forked `ReaderActivity`, so the port is the renderer underneath it rather than the reader, and their TTS is taken as a text layer only, since they have no MediaSession anywhere in their tree and Reikai does.
- **Scanlator filtering is a content-type-gated capability**, manga-only at first and generalizable to novels later; it is deliberately not taken as a tsundoku port, since tsundoku only gets it through novels-as-manga-rows.
- **Migration is incremental and verified per surface**, details first as the keystone. Each surface is independently shippable and on-device verified before the next.
- **A takeover is not complete until the replaced code's behaviour is inventoried (2026-08-06).** Cutting a surface over and verifying it on device is not the bar. Device verification finds what you thought to test, and the migrate surface passed it, then spent five audit rounds with two upstream behaviours silently dropped, both found by accident: the additional search query never reached a search on any route, and a manually picked target was accepted without the refresh upstream refuses one on. So a takeover is done when the replaced code's behaviour has been walked end to end and every item marked present, deliberately dropped with the reason, or missing. The off-path manifest catches upstream changing a file after a takeover; nothing catches what a takeover failed to carry across, and this inventory is that check. It applies to the taken-over surfaces (details, library, migrate); the surfaces being redone at the behavior seam get theirs at their own cutover.
- **The rules that bind live in [.claude/rules/content-layer.md](../../../.claude/rules/content-layer.md), not here (2026-08-06).** That file loads every session and holds the law: the write-once rule and its forward-only scope, the means-not-the-rule companion, the seam-depth table, the ownership rules, the capability-slot and derive-or-do-not-own rules, the pin-once ladder, parity as the default, decline expiry, the delete-and-manifest policy, and the completion bar above. This file keeps the rationale, the measurements and the amendment history, which is what a ruling needs to be re-litigated but not what a session needs loaded to work safely.
- **A selection is pruned to what a surface excluded, never to what navigation hides (owner, 2026-08-12).** Both engines that own a selection had it pruned against a stream taken before the surface finished narrowing, so a selected row could stop being shown and keep being counted and acted on. The rule that settles both: an entry the surface has excluded (a mode's section cap, a chapter-state filter, a hidden category, an emptied bucket, a dynamic group the feed has not caught up with) leaves the selection, because nothing on screen can bring it back without changing a setting; an entry that navigation is hiding (a collapsed category, a pager page one swipe away) stays, because it is still part of what the user is working through. The recents engine now renders in the engine and prunes to the drawn rows; the library assembly publishes the ids it kept and prunes to those. The library case cost a constructor change, since the prune could not be tested at all while the engine resolved its preferences and repository through Injekt internally, and the old wiring compiled green.
