# Content layer: library surface

## Goal

Collapse the manga and novel libraries onto one Reikai-owned content layer, so the library behaves identically for both content types and a library change is written once. This is the library surface of the [content-layer program](content-layer-architecture.md) (after the details surface), built to the same shape: a neutral state, a behavior seam, adapters over the live engines, an `EntryId` identity, and typed capability slots.

## Why

Unlike details, the library UI is already largely shared. Novels render through the same `LibraryTab` and the same grid, hopper, category picker, and settings by disguising each novel as a negative-id `LibraryItem`, and the grouping / sort / filter kernels (`LibraryDynamicGrouping`, `reikaiSortCategories`, `EntryDisplayPage`, the hopper/picker/fast-scroll grid) are already content-neutral. Two forks remain, and both are exactly the anti-divergence hazard the program exists to remove:

- **The ScreenModel pipeline.** `NovelLibraryViewModel` reimplements the manga library's `buildState` pipeline (filter, merge-collapse, tracker union, tracker-status filter, sort, dynamic grouping, custom-info overlay), retyped onto `Novel`. Its own code notes it mirrors the manga library's tracker filter. Every library behavior change is two edits, and the two sides drift.
- **The identity disguise.** Novels ride as negative-id fake `LibraryItem`s so they can reuse the manga-typed shared UI and pipeline. The neutral `EntryId` (already used by the details and cover-cache layers) is unused in the library, so the library still leans on the sign-of-the-id trick the architecture doc wants retired.

## Approach

Three phases, lowest-risk first, each independently shippable and on-device verified (debug and minified), matching the program's per-surface discipline.

**Phase 1: the type-agnostic shared transforms.** A deep side-by-side of the two `buildState` pipelines showed the transform stages are logically congruent, but the filter, merge-collapse, and item-build stages are coupled to the entry type (manga transforms `LibraryItem`; the novel model transforms `LibraryNovel`, collapses into `CollapsedNovel`, then builds `LibraryItem`, and the two collapse at different pipeline positions, manga before filter, novel after). So the type-coupled bulk moves to Phase 2, where the neutral `EntryId`-keyed row lands and both sides share one type. Phase 1 extracts only the genuinely type-agnostic pieces, each safe and independent: the **lewd filter level-up** (a genre-based novel `isLewd`, see the decision below), the **shared sort comparator** (the 11 keys are identical across `LibrarySort` and `NovelLibrarySort`; unify to one comparator builder or a decode-to-shared seam), and the **shared tracker union + mean + tri-state filter** helper (both models compute the same merge-group tracker union and include/exclude tri-state). Two open questions to resolve first: whether manga's `getTracksPerManga` is already merge-group-aware, and whether to unify the two sort enums or keep a thin decode seam.

**Phase 2: neutral state, adapters, `EntryId`.** Introduce a neutral `LibraryScreenState` (rows keyed by `EntryId`, capability slots) and a `LibraryBehavior` seam, with a `MangaLibraryAdapter` over the live `LibraryViewModel` (fenced in `// RK` islands, so a renamed upstream field breaks the adapter at compile time) and a `NovelLibraryAdapter` over the novel engine. `LibraryTab` consumes the neutral state and behavior instead of today's `active*` fall-through (an informal adapter already). Identity moves from the signed `Long` / id-sign branches to `EntryId`, retiring the disguise. This is code-only: no schema migration and no backup change, because novel rows already carry real positive ids and `EntryId.coverCacheKey()` already centralizes the one cover-cache negation. A one-time reset of any runtime cache or UI state keyed by the old disguised id (scroll, selection) is expected and is never a backup concern.

**Phase 3: parity and reconciliations.** Unify the collapsed-set representation (the novel side's single `Set<String>` vs the manga side's split real / dynamic sets), reconcile `NovelLibrarySort` against `LibrarySort`, and finalize the lewd gating and label.

**What stays forked, deliberately (the seams).** The manga and novel engines never merge (different domain models, `String` vs `Long` sources, plugin host vs Mihon sources). The merge-collapse helpers stay forked (different output types, a prior locked decision in [merge-component-consolidation.md](merge-component-consolidation.md)). Download-count derivation stays per-type until the separate download-subsystem unification (Road B). These are injected seams, exactly like the details adapters' `resolveSources` / `setFavorite` lambdas.

## Key files

- Manga library, stays live (engine): `eu/kanade/tachiyomi/ui/library/` (`LibraryViewModel`, `LibraryTab`, `LibraryItem`, `LibrarySettingsViewModel`).
- Novel library, its pipeline dissolves: `reikai/presentation/library/novels/` (`NovelLibraryViewModel`, `NovelLibraryItem`, `NovelLibrarySettingsDialog`, `NovelMergeCollapse`).
- Already-neutral shared plumbing to build on: `reikai/presentation/library/` (`ReikaiLibraryContent`, `ReikaiLibraryState`, `ReikaiLibraryBadges`, `LibraryDynamicGrouping`, `ReikaiCategorySort`, the hopper / picker / fast-scroll grid), plus `EntryDisplayPage`.
- Neutral identity: `reikai/domain/entry/EntryId` (and `coverCacheKey`).
- The template to mirror: `reikai/presentation/details/` (the two adapters, `EntryDetailsScreenState`, `EntryDetailsBehavior`, the `// RK` host composition).
- Lewd heuristic to generalize: `reikai/util/MangaLewd`.

## Status

**The selection prune moved onto the assembly (2026-08-12).** It ran against the providers' rows, which is everything a filter or a search had already narrowed, but not what the assembly went on to drop: a hidden category, a bucket left empty, a dynamic group behind its feed. Those leave an entry in the rows, so it stayed selected, stayed counted and stayed actionable while no screen showed it, and the settings sheet is reachable with a selection running. The assembly now publishes the ids it kept and the prune uses those; collapse and the pager band are deliberately untouched, being navigation rather than exclusion. Pinning it needed the engine to take its preferences and category repository as arguments, because the old wiring compiled and the whole suite stayed green. The cross-surface rule is in [content-layer-architecture.md](content-layer-architecture.md).

**Phase 1 shipped; Phase 2 structural core shipped.** Grounded by a deep code-research pass across both library ScreenModels, the shared library plumbing, the details template, the manga/novel feature gaps, and the novel plugin ecosystem (the lewd-filter viability check).

Phase 1 (the type-agnostic slices) shipped: the novel library lewd filter (`1feb87988`, genre-based `Novel.isLewd` reusing a `hasLewdGenre` helper extracted from `MangaLewd`) and the manga tracker filter + tracker-score sort merge-group-awareness fix (`9953f2680`, both now union member tracks via `relatedMangaIds`, matching the novel library). The deep pipeline comparison resolved the two open questions (`getTracksPerManga` groups per-manga, hence the tracker fix; `NovelLibrarySort`/`LibrarySort` diverge in persisted category-flags bits, the Downloaded and TrackerMean bit values swapped, so a single decoder would misread saved sorts) and showed the sort/tracker pure dedup only shares a skeleton over the current types, so it folds into the pipeline-sharing step rather than a low-value current-type extraction. Two premises from the earlier scoping were corrected by the deep pass: the bit-0 `CUSTOMIZED` sentinel is now parity, not novel-only (manga gained the same per-category-sort override in `CategorySortOverride`), and both content types' filters are per-axis TriState prefs overlapping 1:1 (bar manga's `intervalCustom` and novel's `lewd`), not the "one Long-flag vs three TriState" the premise assumed.

Phase 2's structural core shipped (`2a1ccfea8` identity, `92cd34cf7` seam), behavior-preserving and on-device verified in both view modes and both content types: the neutral `LibraryScreenState` + `LibraryBehavior` seam, a `MangaLibraryAdapter` over the live `LibraryViewModel` and a `NovelLibraryAdapter` over the novel model, and the `EntryId` identity replacing the id-sign decisions in the shared cover/badge code. What remained open at that point, both since done: sharing the pipeline stages themselves (sort via the decode-to-shared-comparator seam, the tracker union + mean + tri-state, the filter over the neutral row, collapse-before-filter) so a filter/sort change is written once, and retiring the negative synthetic leaf id (re-keying the Mihon pager cells' selection onto `EntryId`). Those two are the remaining reconcile items (collapse position, collapsed-set representation, the `LibraryItem`-typed-filter reorder) and the injected seams (merge-collapse, download-count, tracker resolution, category source).

### Remaining sequence

**All seven steps are done and on-device verified**, and so is the **engine step** that followed them (2026-07-23, `fc29c35b9`..`ed983165a`). The engine is scoped in [content-layer-architecture.md](content-layer-architecture.md) under the 2026-07-22 amendment rather than here.

What shipped in it, all device-verified on both the Fold and the A57 across both view modes and both chips:

- **One filter and sort binding over the shared row** (`LibraryItemFields.kt`). Novels now build the row before filtering rather than after, so both content types reach the shared kernels at the same point in the type chain, which is what lets one comparator order a mixed list. Three seams stay explicit parameters: the lewd source-name half (manga-only), tracker ids, and the tracker mean.
- **`LibraryProvider` and `LibraryEngine`.** Each content type is a provider (the neutral behaviour seam plus its type); the engine owns the selection as `Set<EntryId>`, every operation on it, and bulk-action dispatch. `providersFor(ALL)` already fans out to both; `behaviorFor(ALL)` fails loudly, since a mixed view still needs one category id space.
- **Row identity through the grids.** The grid callbacks carry `LibraryItem` rather than its `LibraryManga`, so opening an entry and resuming reading follow the tapped row's own content type instead of the active chip. Four of the tab's 22 `isNovels` branches went away, and those four were the ones a mixed list would have got wrong.
- **Reikai logic out of the Mihon model.** 203 lines of net-new Reikai code (the display-state flow, the collapse and hopper setters, dynamic grouping) moved to `reikai.presentation.library`; `LibraryViewModel` went 1316 to 1056 lines and its largest `// RK` island 203 to 46. The file stays live and synced rather than being manifested, since it is an engine file.

Two bugs surfaced while writing the test plan for that work, which is a habit worth keeping: switching the content-type chip carried the shared selection into a view where none of its rows were listed (a regression from the selection move), and single-list Select all acted on the first category rather than the one scrolled to (**pre-existing**, inherited from the model's `selectAll`, which read the pager index the single-list view never updates).

The category axis is no longer what the All chip is waiting on: the category-schema unification shipped, including user-creatable universal categories and their backup support, so there is one `categories` table and one id space (see [category-schema-unification.md](category-schema-unification.md)). What remains is the library screen itself, planned as an All-first rebuild in which the manga and novel chips become filters over one assembled list rather than two states to combine.

## The All-first takeover (planned 2026-07-27)

Decided after auditing the surface: the pipeline kernels (filter, sort, grouping, field extraction) are genuinely shared and called by both models, but `LibraryBehavior` is a 15-method passthrough with nothing implemented in the shared layer, and `LibraryTab` bypasses it for refresh, continue-reading, open-random, the hopper long-press, migrate and all dialog rendering, including three methods the interface already has (`search`, `toggleAllCategoriesCollapsed`, `openSettingsDialog`). So the library is unified at the pipeline layer and not at the behaviour layer.

Five phases plus one follow-on slice, each shipping alone and device-verified in **both** view modes (tabbed pager and single-list hopper).

1. **Ground-clearing (shipped, `3f1e8c3c0`, `0f2828687`).** Manifest enforcement made a hard stop; `LibraryCategoryRef` deleted; four stale claims corrected; the manga Change-categories dialog switched to a fresh category read, which was a live bug (a hidden category could not be picked).
2. **Close the behaviour seam: shipped.** Both slices are in and device-verified, so nothing in the tab reaches past `LibraryBehavior` / `LibraryEngine` for a dialog or a verb any more, and the `isNovels` branch count went 22 to 10. Move the bypassed `LibraryTab` calls onto `LibraryBehavior`; collapse the two per-type dialog streams into one, **owned by `LibraryEngine`**. Nothing can fan out over methods that do not exist on the interface, so this gated everything after it.
   **Scoped out, deliberately:** the display config the tab reads off the manga model on both chips is one library-wide setting, so it is hoisted to a shared holder rather than duplicated per type, and the `state.reikai` block behind it waits for phase 3. Per-type navigation needs nothing: `openEntry` and the resume handler already dispatch on the row's own `EntryId`.

   **Slice 1, the dialog collapse: shipped (`b8a40e7ed`), device-verified** on the emulator across both chips, both view modes, and merged selections of two and three sources, with the whole library data byte-identical afterwards.    - `Settings` carries its content type, because `NovelLibrarySettingsDialog` takes the novel ScreenModel as a parameter and cannot be neutralized before phase 2.5. Keying the render branch on the dialog rather than on the ambient chip is what a mixed list needs anyway.
   - The engine needs a coroutine scope for the category reads. It landed as an androidx `ViewModel` with an assisted factory rather than the Voyager `ScreenModel` planned here, which is the shape the rest of the app moved to. Once the engine builds dialogs, those bodies are dead Reikai code inside a Mihon file. The novel model's dialog union and openers are Reikai-only with no upstream twin, so they are deleted in this slice.

**Settled before phase 2: tracker propagation (2026-07-27).** The two content types were not one design at two timings, they were two invariants. The dedup picks the furthest-read row per tracker rather than the first, so the duplicate rows older builds already wrote are tolerated without a migration. The upstream cost is two small `// RK` islands in `TrackChapter` and `RefreshTracks`, files upstream has not touched since February 2024.


### Engine-step ground truth (2026-07-23)

Verified against current code before starting the engine. These are the facts the engine design turns on:

- **The two pipelines convert to the shared row at opposite ends.** Manga builds `LibraryItem` inside `getFavoritesFlow`, then collapses, filters and sorts over it. Novels collapse into `CollapsedNovel`, filter over that, sort over `LibraryNovel`, and call `toLibraryItem` last. The shared kernels are genuinely shared as functions, but each side binds a different `T`, and the novel bindings are pre-conversion domain types. A mixed list has to compare a manga row against a novel row at the sort stage, so this is the constraint the engine design turns on, not categories or source ids.
- **The novel row is already nearly complete as the shared row.** Its synthetic `Manga` carries status, genre, categories, bookmark and read counts and the dates, and the novel status codes line up 1:1 with `SManga`'s. The gap is `source`, left at the factory default, so shared code reading `libraryManga.manga.source` on a novel gets a meaningless value.
- **Novel selection re-runs the whole pipeline for nothing.** `selection` is an input to the main combine but is only written into the state at the end, never read by filter, sort or grouping, so every selection tap re-runs collapse, filter, sort, grouping and item build. Manga keeps selection out of its flow entirely. Novel search also lacks manga's `distinctUntilChanged` plus debounce. A memoized language-code cache already works around the symptom.
- **No shared combine above both providers.** `getFavoritesFlow` combines the manga download-cache tick with two unconditional full-table batch reads (search tags and titles) plus a merged-unread query on every emission. The reads are database batches, not a network scan, and are not gated on metadata sources; today the two download caches are separate classes, so novels cannot fire them. Merge the two providers' upstream flows and they would.
- **Dynamic grouping was only half All-ready.** Bucket ids are index-assigned in one call and collapse keys on name, both fine for a mixed list, but the item id was a raw `Long` shared by the metadata maps, so a mixed call would have de-duplicated a manga and a novel sharing a row id and cross-read their source, language and status. Fixed by making the kernel generic in the id (`fc29c35b9`).
- **The category id spaces were disjoint, and are not any more.** This was written when `categories` and `novel_categories` were separate rowid tables allocating independently. The schema unification folded them into one table with a `content_type` column, so there is a single id space. `LibraryCategoryRef` (`fc29c35b9`), which existed to pair a category with its content type, was deleted unwired once it had nothing left to disambiguate.
- **The engine is an evolution of one line.** Both models and both adapters are already constructed and both states collected eagerly; `LibraryTab` just picks one. The engine replaces the pick with something that can also merge. All 22 `isNovels` branches live in that one file.

Each step is independently compilable and verifiable, and carries its own tests rather than depending on an upfront test pass. That shape is forced by what is testable: the novel comparator, both collapse helpers, the sort-override decoder and the grouping kernel are pure and reachable, but the manga comparator and filter predicates are private local functions inside `LibraryViewModel` and `applySort` reads an Injekt-constructed `trackerManager`, so they cannot be pinned until the step that extracts them. Bulk-action expansion needs the whole ScreenModel and is verified on-device, not by unit test. Library-pipeline tests run under `:app:testDebugUnitTest`, not `:domain:test`.

1. **Pin the novel sort comparator.** Characterisation tests over all 11 modes, both directions, the tiebreak, tracker-mean defaults and Random stability, with the three known divergences pinned and annotated so step 5 gets a clear signal. **Done** (`70f6b8dde`).
2. **Merge-aware bulk actions.** Mark-read and change-categories expand to the whole group on both content types; delete keeps its checkbox but defaults on for merged selections. **Done** (`3538690c9`), owner-verified. Downloads deliberately do NOT expand (see the rulings above), and the download-availability gate still reads anchors only, which moves to step 3.

Novels are unaffected (they never expose Download-lock and have no local concept). The pre-existing multi-select `fastAll { !isLocal }` semantics are left as-is (out of scope; truly per-source download in a mixed multi-select needs the deferred download-aggregation machinery).
4. **Grouping fixes.** Done (`034375009`). Two gaps in BY_TRACK_STATUS grouping: manga read only the representative's own tracks (unlike its own filter and sort), and neither content type passed `trackingStatusOrder`, so the grouping kernel's reading-progress order (Reading first, Dropped last) never fired and groups sorted alphabetically. Manga now unions member tracks over `relatedMangaIds` (matching the filter/sort union and the already-merge-aware novel side, whose `tracksByRep` was union-keyed), and both sides now pass a `trackingStatusOrder` built from the logged-in trackers' own `Tracker.getStatusList()` order. The order builder is a shared pure helper (`LibraryTrackingStatusOrder`) so the two libraries can't drift; it is unit-tested and the kernel's `trackingStatusOrder` contract already had a characterisation test. The reading-progress order is verified on-device; the manga merge-aware grouping is not separately exercised there but mirrors the already-shipped, already-verified filter/sort union exactly.

   The reading-progress order also now **ignores the alphabetical category sort** (owner ruling): tracking status has an inherent order, so the A->Z / Z->A category sort (meant for name-keyed groupings) no longer applies to it, and BY_TRACK_STATUS always sorts by progress. Previously the intent order fired only when the category sort was left at its default, so a user with A->Z set (a global preference) saw a meaningless alphabetical status order. Z->A no longer reverses track status; the reversal was judged useless for statuses and dropped for simplicity.
5. **Sort.** Done (`eadbcfc56`). Verified on-device (both libraries, clean logs). Both libraries now sort through one shared pure `librarySortComparator<T>` (`domain/.../reikai/domain/library/LibrarySortComparator.kt`) over a `LibrarySortFields<T>` accessor bundle, so the comparator never depends on the concrete row type and no per-entry wrapper is allocated. Both content types decode their persisted flags through the shared `sortForCategory` and map `LibrarySort.Type` to a neutral `LibrarySortMode`. There is one flags layout: the category-schema unification translated the novel rows onto the manga one (`MigrateNovelCategoriesToSharedTableMigration`, 187f), retiring `NovelLibrarySort`, so no per-type decoder remains. The manga `applySort` is a `// RK` patch that decodes `LibrarySort`, builds the accessors, and calls the shared comparator, dropping the local comparator, the `shuffled` Random short-circuit and the `error()` branch.

   Four reconciliations, per the pipeline-share rulings plus one new finding: the alphabetical tiebreak stays A->Z under a descending sort (manga form), zero-unread entries sort last regardless of direction (manga form), Random is a per-id seeded comparator (novel form), and, newly surfaced by the deep pass and owner-ruled, alphabetical uses the locale collator (manga/upstream form), leveling novels up from plain code-point ordering. The three annotated novel divergence tests were flipped to the shared form (not deleted). The manga tracker-mean precompute was fixed to the novel's form (dedup by tracker id, drop non-positive scores, guard on the mapped scores not the raw track list), killing upstream's bug where an all-logged-out track list averaged to `NaN` and sorted above every real score. Pinned by a new `LibrarySortComparatorTest` (13 cases) plus the updated novel test.
6. **Filter, tracker filter, collapse position and search.** Done (`8cbda6eb6`). On-device verified on the Fold (the app compiles and runs, the novel search level-up and the filters work, logs clean). Collapse-before-filter was already standard on both sides (it shipped with the merged-count reorder), so this step is the filter + search share. The filter unified behavior-preservingly: a pure `libraryFilterMatches` over a `LibraryFilterFields<T>` accessor bundle (`reikai.presentation.library.LibraryFilter`), with the tracker axis folded in (both sides already merge-aware) and the per-type seams in the accessors (downloaded's local-source concept, lewd's source-name check, manga-only interval, the merge-group tracker union). The novel's separate tracker-status pass folded into the one filter. Search levelled the novel library up to the manga grammar via a shared `libraryQueryMatches` (`id:`, `src:` through a per-type accessor since a manga source id is a Long and a novel source a String slug, description, source-name, comma-separated negatable terms); the manga `LibraryItem.matches` keeps its metadata-source tag grammar as a manga-only pre-check on non-prefix queries, then delegates the plain-text to the shared core, and its now-dead searchTags plain-text clauses were dropped safely (a non-metadata manga never carries them, and a metadata source never reaches the plain-text branch). Placed in the app module (not domain like the sort), because the filter needs `matchesCategoryFilter` / `isLewd` / `NovelSourceManager`, which live there alongside the grouping and tracking-status kernels. Pinned by a new `LibraryFilterTest` and `LibraryQueryMatchTest`.
7. **Retire the negative synthetic leaf id**, re-keying selection and the Mihon pager cells onto `EntryId`. Split in two, since only the second half touches user data.

   **7a, the identity re-key: done (`b0932591b`), verified on-device** (A57, both view modes and both libraries: select, range, select-all, invert, scroll-and-return, tap routing, the merged-selection actions, and novel resume; selection is device-independent, so the Fold adds nothing here). The novel row carries the novel's own id (the mapper's negation and the seven sites that undid it are gone), and the neutral `LibraryScreenState.selection` is a `Set<EntryId>` rather than a `Set<Long>`. Each adapter stamps its own content type on the way out, so both ScreenModels keep their raw-id selection internally and Mihon's stays unpatched, which is also why the manga model was not re-typed: the library engine supersedes that selection anyway, so re-typing ~90 verbatim upstream lines would be work thrown away. Every cell compares `libraryItem.entryId in selection`, and the single-list cell key gained the content type so two entries sharing a row id cannot collide in one grid. Mihon's own grids pass no item key at all (positional identity), so "re-keying the pager cells" turned out to be one Reikai-owned string key, not a Mihon change. Pinned by `NovelLibraryItemTest` over the pure row mapper.

   **7b, the cover-cache namespace: done (`075b38e34`), upgrade verified on-device** (a hand-set manga cover and a hand-set novel cover both survived an install over the previous build, which is the pair that matters: the novel proves the migration ran, since the new name would otherwise read as no custom cover, and the manga proves its key stayed byte-identical). `CoverCache` stores every custom cover in one directory named by the hash of the id, under `getExternalFilesDir` (durable user data, not an evictable cache), so the negation was the only thing keeping novel 12 and manga 12 apart there. Retiring it was a namespace change, not a sign removal: `CoverCache` gained an `EntryId` overload beside the upstream `Long` one, hashing a qualified name (manga stay `"12"`, byte-identical, so nothing on the manga side moves; novels become `"novel:12"`), and `MigrateNovelCustomCoverKeysMigration` (`186f`, with the matching `versionCode` bump) copies then deletes each novel's old file, best-effort per novel so a failure leaves the old file rather than losing a hand-set cover.

   The single `coverCacheKey(): Long` split into two named projections, because it was serving two unrelated caches: `customCoverKey(): String` for the on-disk file, and `vibrantColorKey(): Long` for `MangaCover.vibrantCoverColorMap`. **The negation deliberately survives in the second**, and only there: that map is upstream and `Long`-keyed, and it rebuilds itself on the next cover load, so patching Mihon's key type to remove a disguise from a throwaway cache is not worth the sync cost. This also means the colour cache needs no migration and no prune, which an earlier version of this plan assumed it would. The on-disk contract is pinned by `EntryIdKeysTest`: the manga key must stay the plain id, or every existing manga cover orphans.

## Decisions & tradeoffs

- **Match the details architecture** (neutral state + behavior seam + adapters + `EntryId`), not a lighter pipeline-only helper, so the whole content layer is one cohesive shape rather than two. Owner-chosen.
- **Extract shared behavior before dissolving the novel model** (Phase 1 before Phase 2), per the program's rule, so each step is incremental and never gambles the whole surface on one big adapter.
- **Retire the negative-id disguise via `EntryId`** (Phase 2). It works today and is code-only, but leaving it forks identity from the rest of the content layer; unifying it is the point of the full collapse.
- **Level novels up on the lewd filter (genre-based), not gate it.** Novel sources carry no nsfw flag (neither the plugin metadata nor the novel model has one, and LNReader has no adult concept), but adult genre tags (`mature`, `adult`, `smut`, `erotica`) are common across the novel plugin ecosystem, so the existing genre heuristic in `MangaLewd` classifies them. Only the manga source-name branch is inapplicable to novels. In-app copy should note that novel lewd-detection is genre-tag-based, so it is weaker than a hard source flag.
- **`LibraryViewModel` and `LibraryTab` stay live and `// RK`-patched** (engine / partially-collapsed files), never dissolved or added to the off-path manifest while a live remainder exists, per the [upstream-sync](../upstream-sync.md) policy. **Amended 2026-07-22, scoped to this surface:** the shared layer takes over selection and pipeline orchestration, because the "All" chip's mixed manga plus novel list makes a selection neither ScreenModel can own (a range-select spans both types). `LibraryViewModel` still stays live and on the render path as the manga provider, keeping its favourites flow and its action verbs (read, download, delete, categories) and its Mihon interactor calls. Full reasoning in [content-layer-architecture.md](content-layer-architecture.md), "Decisions & tradeoffs".
- **The merge-collapse helpers and the download-count derivation stay per-type seams**, not shared code.
- **Sort unifies through one shared comparator over one persisted flags layout.** `LibrarySort` and `NovelLibrarySort` once stored the Downloaded and TrackerMean bits with swapped values, so the sort share landed as a decode-to-shared-comparator seam with a per-type decoder and no data rewrite, deliberately avoiding a migration for a cosmetic gain. The category-schema unification then moved novel categories onto the shared table and translated their flags to the manga layout (`MigrateNovelCategoriesToSharedTableMigration`, 187f), so both types decode through `sortForCategory` and `NovelLibrarySort` is gone.
- **Retire the id-sign decisions first, the negative leaf id later.** The `EntryId` identity (shipped) routes the shared cover/badge decisions off the id's sign; the leaf row still carries the negative synthetic id as a mechanical key, retired when the pipeline stages are shared and the Mihon pager cells re-key onto `EntryId`.
- **The shared row is Mihon's `LibraryItem`, and novels level up to it before filter and sort (2026-07-23, owner-chosen).** The engine step needs one row type at the sort stage, because a mixed list compares a manga row against a novel row there. Three shapes were weighed. Merging two independently sorted per-type lists at the end was rejected: it produces a correct mixed list but leaves both pipelines forked, so a new filter axis is still two edits, which is the "seam drawn too high" failure this program exists to remove. A net-new neutral row type was rejected as the same collapse at higher cost, since every grid composable consumes `LibraryItem` and would need re-typing. So novels convert earlier instead and the shared pipeline runs over `LibraryItem`, which already carries the neutral `EntryId` as its identity and which novels already produce. This is not novels-as-manga: that rejected design is about the storage layer, and novels keep their own tables and engine. Corollary, corrected after reading `LibraryItem` properly: the row cannot be made honest about its source, and should not try. `Manga.source` is a `Long` and a novel source is a String slug, so there is no valid value to put there, which is why the row already carries novel source facts out of band (`badges.coverSite`, `badges.sourceIconUrl`). The live hazard is that `LibraryItem.matches` resolves the source itself through the manga `SourceManager`, so a novel row reaching it would match against a stub. Novels avoid that today only by calling the shared query matcher directly. So the shared pipeline takes source-derived facts (the name for search, the id for `src:`) from a per-entry side channel keyed by `EntryId`, merged by the engine from both providers, exactly as the grouping kernel now takes its metadata maps. That keeps one uniform accessor bundle with no content-type branching inside the shared layer, and no faked source id.

### Pipeline-share rulings (2026-07-21)

A deep pipeline comparison found eleven behavioural differences between the two `buildState` implementations, plus a systemic merge-awareness gap. Rulings, to be applied as the stages are shared:

- **Collapse before filter (manga's order) wins**, but only after the representative is fixed (next bullet). Collapsing first avoids double-counting chapters that grouped sources share, and keeps the row stable when filters toggle. Filtering first (the novel order) lets a group's cover and title change as filters change, and surfaces entries whose "unread" chapters the user already read on the primary.
- **The collapsed representative must honour the persisted source ranking.** Today both collapse helpers pick by most-chapters-then-earliest-added and never see `merge_group_manga.source_priority`, so a manual reorder on the details screen is ignored by the library: the row shows one source's cover, title and unread count while the details chapter list is trunked on another. Fix by reusing the ranking chain the aggregation already implements (per-group override, then the global preferred-source list, then chapter count). Note `merge_group.title_override` / `cover_override` exist but are never written, and would be the cleaner long-term home for an explicit pinned title/cover.
- **Bulk selection actions expand to the whole merge group, except downloads.** Mark-read and change-categories act on the anchor only today, on both content types, because the collapse drops members out of the emitted list and every action reads the anchor-only derivation. Both models already carry the expanded derivation; it was written for the delete flow and never propagated. Expansion becomes automatic for those two; delete keeps its explicit checkbox (destructive) but defaults on for merged selections.
- **Downloads must never fan out across a merge group.** Grouped sources carry the same chapters, so downloading every member fetches each chapter once per source and burns storage on near-duplicates. The correct target is the group's deduplicated list, which is what the details screen already downloads: it acts on the visible list (the "All" aggregation, or one source when a chip is selected) and groups by each chapter's own `mangaId`, so every chapter is fetched once from its origin source and the ranking override is respected. The library resolves the same list on the selection path, through `MergedChapterProvider.load` for manga and `GetNextNovelChapter.groupChapters` for novels, and skips a chapter any member already holds on disk.
- **Sort unifies via a decode-to-shared-comparator seam**, per the existing decision, reconciling three real differences: the alphabetical tiebreak stays ascending under a descending sort (manga's form, matching upstream), zero-unread entries sort last regardless of direction (manga's form), and Random becomes the per-id seeded comparator (the novel form, the only one expressible as a comparator rather than a short-circuit around one).
- **Tracker mean drops non-positive scores** (the novel form: an unrated tracker is unscored, not zero) and **dedupes by tracker id** (the novel form). Manga's guard tests the raw track list rather than the mapped score list, so an entry whose only tracks belong to a logged-out tracker averages an empty list to `NaN`, which is non-null and therefore escapes the `-1.0` fallback and sorts above every real score. This is upstream's bug verbatim; fix locally.
- **Tracker-status grouping becomes merge-aware on manga** (it reads the primary's tracks only, unlike its own filter and sort), and both sides pass `trackingStatusOrder`, which neither does today, so the intent ordering the grouping kernel implements never fires.
- **Novel library search levels up** to the manga matcher's capabilities (`id:`, `src:`, description, source name, comma-separated negatable terms). The metadata-source tag grammar simply never matches a novel, which is acceptable rather than a faked feature.
- **The library unread badge keeps the representative's own count for this phase.** The merged (deduplicated) count is a scoped follow-up, not part of the pipeline share, because it needs a new table and a `.sqm` migration, a different risk class from the Kotlin-only stage sharing.

### Merged unread count (follow-up, designed not built)

A chapter counts as **read when any member source's copy of it is read**, applied consistently to both the library badge and the details "All" chapter list, so the two never disagree.

Cache the dedup **mapping**, never the count. Read status is not an input to either aggregation, so reading can never change which chapters are duplicates, whereas the count changes on every chapter read and would be stale almost immediately. A canonical-chapter set per merge group (new table beside `merge_group_manga`, with a novel twin) is rebuilt only on chapter-list changes, membership changes, source-order override changes, preferred-source changes and excluded-scanlator changes; the count is then a live SQL join over that set and the `read` column, the same cost class as the aggregates `libraryView` already computes.

A pure-SQL count with no cache was considered and rejected: it works for manga, whose dedup key is the chapter number narrowed to `Float`, but not for novels, whose key is a Kotlin-normalized title string. Taking it would have re-split the two content types, the exact failure this initiative exists to prevent. Recomputing the aggregation per library emission was also rejected: it loads full chapter rows per member, so a library with a few dozen merged groups adds on the order of a hundred queries per emission, and emissions fire on every preference change and DB invalidation.
